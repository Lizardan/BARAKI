## Общий баг: заклинания кастовались одновременно (без очереди)
- Симптом от пользователя: «если не в КД — кастуются одновременно; должны кастоваться
  только по очереди, следующее — только после окончания анимации каста».
- Корень: `MatchCombatSystem.ApplyAbilityAnimLock` делал `return` когда
  `kind == AbilityAnimKind.None && AnimState == ""`, поэтому `CastLockRemainingSeconds`
  оставался 0 → `TickUnit` не блокировал новый каст → следующий слот кита кастовался
  на следующем тике. Все активные способности с непрописанной анимацией (в т.ч. новые
  заклинания Древних BlightingGaze/VoidDrain/RaiseDrowned, ветеранские KingsCommand/Aegis/
  Sanctuary/GreaterColossus) страдали от этого.
- Фикс (2 правки):
  1. `AbilityAnimRules.ResolveKind` — добавлены `BlightingGaze or VoidDrain or RaiseDrowned
     => AbilityAnimKind.Cast` (явная классификация заклинаний Древних → 1.5s staff-cast lock).
  2. `ApplyAbilityAnimLock` — убран early-return; теперь при `lockSeconds <= 0f`
     ставится `AbilityAnimRules.StaffCastClipSeconds` (1.5s). Это общая гарантия: любая
     активная способность, прошедшая через каст (а пассивы/ауры сюда НЕ попадают —
     `TryCastKitAbilities` фильтрует `def.IsActive`), получает минимальный cast-lock и
     не может перекастовываться каждый тик.
- Поведение: спеллы теперь строго последовательны; следующий каст — только после истечения
  `CastLockRemainingSeconds` предыдущего.
- Тесты: поправлен `FacelessSpellRulesTests.FacelessCaster_MagicLevel2_CastsVoidDrain_...`
  (Drain раньше ждался на следующем тике, теперь — после истечения каст-лока ~1.5s; тик
  заменён на цикл 15×0.1) + добавлен `FacelessCaster_SpellsCastSequentially_NotSimultaneously`
  (проверяет CastLock>0 после каста и что второй спелл не стартует, пока лок не истёк).
- **Верификация Compile/EditMode НЕ выполнена** (Unity Editor открыт, unityMCP без Trust) —
  статический разбор пройден: поле `CastLockRemainingSeconds` есть в `MatchUnitState`,
  `AbilityIds.*` доступны в `AbilityAnimRules`, ни один тест не ассертит `BehaviorState`
  для None-способности, single-cast ассерты ветеранских/билдинг-тестов не задеты.
- Статус: правка готова, ждёт Compile+EditMode (Trust unityMCP или ручной прогон в Unity).

- Корень: `BonusPickRules.GetSlotDisplayName/GetSlotDescription(slot)` были захардкожены под
  Human («King Veteran», «March Discipline», описания Human-бонусов) и не знали о расе.
- Фикс: оба метода получили `raceId` (дефолт `RACE_HUMAN` — старые тесты не сломались);
  добавлены Faceless-ветки по канону `wiki/rules/faceless-unit-bonuses.md`
  (Hunger of the Old One … Void Bastion).
- Решение пользователя: **реализованные слоты доступны, нереализованные — серые**.
  Добавлено: `BonusPickRules.FacelessImplementedSlots = {1..6}`, `IsSlotImplemented(slot, raceId)`,
  `IsSlotAvailable(slot, raceId)`; `GetRandomSlot(random, raceId)` (Faceless роллит только 1–6);
  `FillTimeoutPicks(picks, random, raceIds)` + `_raceIds` в `MatchController`.
  `TrySetBonusPick` теперь авторитетно отвергает недоступный слот.
- `BonusPickController`: текст/доступность/тултип по расе, нереализованные слоты disabled + класс
  `bonus-pick__slot--locked`, тултип дописывает «(в разработке)».
- Тесты: +5 кейсов в `BonusPickRulesTests` (Faceless имена 1–12, описания непустые,
  доступность 1–6 / недоступность 7–12, Human держит все 12, random только по доступным).
- Портретов для Faceless-бонусов нет → слоты 1–6 показываются текстом (фолбэк уже был).

## Фикс: иконки бонус-пика Faceless + синий огонёк над бонусными юнитами
- Проблема: в оверлее бонус-пика у Древних показывались портреты Людей. Корень: в
  `UnitVisualCatalog.asset` у Faceless-сета все `_*BonusPortrait` поля указывали на те же GUID, что
  и Human-bonus-портреты (сет склонирован с Human). Human-бейкер честно early-return'ит для не-Human
  (`UnitPortraitBaker.BakeRace`, строка ~98), так что сам не заливал — загрязнение из клонирования ассета.
- Фикс 1 (иконки): `UnitVisualCatalog.TryGetBonusPortrait(raceId, slot, ...)` теперь для
  `raceId == RACE_FACELESS` возвращает `UnitVisualSet.GetBonusPortraitFallback(slot)` — обычный
  портрет юнита/героя расы (слот 1→Melee … 6→Super, 7→Hero1 … 10→Titan). Human не задет.
  Добавлен `using Game.Core;`. Ассет не правили (runtime-оверрайд его обходит; поля оставили,
  помечены как временные в комментарии).
- Фикс 2 (огонёк): вместо смены модели для бонусных/ветеранских юнитов Древних — маленький синий
  огонёк над головой. `MatchCombatPresenter.CreateUnitVisual`: для `unit.BonusSlot > 0 &&
  raceId == RACE_FACELESS` зовёт `AttachBonusFlame(root, visualHeight)` (ставит GO `BonusFlame` на
  `visualHeight + 0.15` и вешает `BonusFlameMarker`). Модель остаётся базовой (у Древних bonus-префабы
  и так null → `GetPrefab` отдаёт базу).
- Новый файл `Runtime/Gameplay/Match/BonusFlameMarker.cs`: MonoBehaviour, сам рисует мягкую синюю
  спрайт-текстуру (радиальный градиент, кешируется статикой), 2 слоя (glow+core), мерцание/бобинг в
  `Update`. SpriteRenderer не считается `UnitVisualHeight` (только Mesh/SkinnedMesh) → не искажает
  collider/бары. Уничтожается вместе с юнитом.
- **Compile/EditMode НЕ прогонялись** (Unity Editor открыт, unityMCP без Trust). Статически: API
  совпадают, `GameIds` доступен в обоих файлах, namespace `Game.Gameplay.Match` у маркера и презентера
  совпадает, тестов на `TryGetBonusPortrait` нет (не сломаются).
- Примечание: огонёк — временный плейсхолдер «пока нет бонусных моделек»; когда появятся реальные
  Faceless-bonus-префабы/портреты — убрать ветку Faceless в `TryGetBonusPortrait` и `AttachBonusFlame`.

## Баг «красная капсула» у бонусного юнита Древних из барака
- Симптом (от пользователя): бонусный Древний (юнит слота 1) из барака спавнился красной капсулой
  вместо нормальной модели (+ просили проверить, что кнопка барака даёт не-улучшенный юнит как
  не-улучшенный).
- Корень №1 (несогласованность путей спавна): вычисление `bonusSlot` для Древних шло по-разному.
  - Авто-волна `MatchCombatSystem.HandleWave` (строка ~647) звала НЕ-расово-осознанную
    `EffectiveBonusSlotForRole(pick, role)` → гейт `NoBonusKitRaceIds` не срабатывал → Древним
    уходил `BonusSlot=1`.
  - Кнопка барака `MatchController.TryManualCallUnit` (строка 1049) звала расово-осознанную
    `EffectiveBonusSlotForRole(player.RaceId, pick, role)` → гейт для Древних давал `BonusSlot=0`.
  Результат: один и тот же бонус-пик Древних давал разный `BonusSlot` в зависимости от пути спавна.
- Корень №2 (капсула): `MatchCombatPresenter.CreateUnitVisual` падала в `CreateFallbackCapsule`
  (красная капсула), если `TryGetPrefab(..., bonusSlot)` вернул false. У Древних `_*Bonus` префабы
  = null → `GetPrefab` в норме отдаёт базу через `??`, НО любой краевой случай, когда enhanced-лук
  возвращает пустую/битую ссылку (напр. стейл-ассет), давал капсулу вместо базовой модели. Огонёк
  (`BonusFlameMarker`) вешается только ПОСЛЕ создания модели, поэтому сам по себе капсулу не вызывает.
- Фикс A (капсула невозможна): новый хелпер `MatchCombatPresenter.ResolveModelPrefab(raceId, unit)` —
  сначала enhanced-префаб, при null/пустом — БЕЗУСЛОВНО базовый префаб расы/роли, и только если и его
  нет — красная капсула. Гарантирует: нет базовой модели → капсула; есть → никогда не капсула.
- Фикс B (согласованность): кнопка барака (1049) переведена на тот же НЕ-расово-осознанный
  `EffectiveBonusSlotForRole(player.BonusPickSlot, role)`, что и авто-волна. Теперь бонус-пик Древних
  в обоих путях течёт → `BonusSlot>0` → базовая модель + синий огонёк; статы остаются базовыми
  (гейт в `UnitStatsResolver` не снят — это #70). «Не улучшенный» пик (нет совпадения роли) →
  `BonusSlot=0` → обычный юнит — в обоих путях.
- Human от Фикса B не меняется (race-aware и non-race-aware перегрузки дают один результат), тесты
  `BarracksManualCallControllerTests` (MvpDefault = Human) остаются валидными.
- Тесты: добавлен `BarracksManualCallControllerTests.TryManualCallUnit_FacelessBonusPick_FlowsSlotKeepsBaseStats`
  (Древний + бонус-пик мувла → `BonusSlot==1`, но `AttackRange==1.5` и `MaxHp==120`, т.е. базовые
  статы, не бонусные).
- **Compile/EditMode НЕ прогонялись** (Unity Editor открыт, unityMCP без Trust). Статически: сигнатуры
  `MatchConfig(int, IReadOnlyList<string>)` и `TryGetPrefab` совпадают; `MatchUnitState.BonusSlot/
  HeroSlot` доступны; `GameIds.Races.Faceless` в `Game.Core` (using уже есть в тесте).
- Следующая карточка: #70 FACELESS-014 (снять `NoBonusKitRaceIds`, подключить `FacelessBonusUnitRules`
  в резолвер статов/спавн — тогда бонус-статы Древних реально применятся, а не гейтятся в базу).
